# Host-aware persistent MoE kernels (MOE_PERSIST=1) for DeepSeek-V4.1 on the GB300

Status 2026-11-04: implemented, measured standalone (stage ii) and in the server (stage iii). **Not promoted**:
`~/dsv41/moe` is unchanged. The candidate start script is `cand/serve-moe-persist.sh`. It is production `serve-moe.sh`
with the production plugin plus the three persist files, and `MOE_PERSIST=1`. Design and history: `DESIGN.md`.

## What it does
Each decode-size MoE call (at most `MOE_PERSIST_MAX_TOKENS` = 128 tokens) runs on the host-aware path. Prefill chunks over
128 tokens and the DSpark draft MoE stay on TRT-LLM. The path is four launches, all CUDA-graph safe and chained with PDL:

1. **front** (Triton, `persist_front.py`, v2). It builds the routing record v2:
   * expert-major 8-row tiles, cold tiles first;
   * the per-GEMM split (`kc`, `hoc`), taken from a bandwidth model;
   * the compact permutation;
   * it gathers the MXFP8 rows and scales.
2. **GEMM1 / GEMM2** (CuTe DSL, `persist_moe_cute.py`, generated by `make_persist_cute.py` from the image's TP4
   routed-expert kernels). They are persistent: one CTA per SM, with 6- and 10-stage TMA pipelines and the TRT-LLM-gen
   epilogue PTX.
   * CTAs `[0, kc)` stream every cold item (weights in host DRAM, over NVLink-C2C), then `hoc` hot items.
   * CTAs `[kc, 152)` stream HBM items.
   * Host reads and HBM reads therefore overlap inside one launch.
3. **finalize** (Triton). It runs only when vLLM does not defer the top-k reduction to mHC (more than 16 tokens).

## Results

### Stage i: exactness, standalone (`src/pdebug.py`, `src/pkb.py` CHECK)
* **Rows match TRT-LLM bit for bit with non-split-K tactics.** Per-route GEMM2 rows are bit-identical for:
  * every non-split-K tactic tested: autotuned, `16:388`, `8:71`, `32:119`, the t128x8x512 path;
  * T = 1, 6, 32, 64, 96, 128, 192;
  * 0 to 18 host-resident experts. Host-resident and HBM-resident experts give the same bits.
* **Against production's split-K `8:437`** (bucket ≤ 8 tokens) the difference is ≤ 4 bf16 ulps (relative ≤ 0.3 %).
* **CPU fp32 reference** (`ref_layout.ref_moe`): cosine 0.999999.

### Correctness in the server
* **Teacher-forced prefill logprobs** (`tf_logprobs.py`, 352 tokens) are bit-identical to the production reference
  (mean |d| 0, max 0). Texts 0 and 1 (112 and 99 tokens) went through the persistent kernels; text 2 (141 tokens) through TRT-LLM.
* **Long prompt:** the 210k-token prompt takes 4.1 s, the same as production.
* **Concurrent argmax check** (30 concurrent greedy requests, re-scored teacher-forced): 3.09 % and 2.33 % of tokens are
  not the argmax, max gap 1.375. Production measured 3.11 % with max gap 1.50, so the persist runs are at production's noise floor.
* **Single-request greedy decode** differs from production on 6 of 6 prompts, at tokens 5–46, mostly at near-ties.
  * This sensitivity is not specific to the new kernel. A control run (`chain3.log`, static placement) kept production's
    TRT-LLM path and changed only the tactic of the 8-token bucket, from split-K `8:437` to `16:388`. It also diverged on
    6 of 6 prompts, at tokens 35–70, with prefix max |dlogprob| up to 0.45.
  * Every output is coherent.
* **Argmax noise floor**, measured in the same session on the candidate and on the restored production server.
  Both are greedy outputs re-scored teacher-forced through the TRT-LLM prefill path.

  | check | candidate (persist) | production |
  |---|---|---|
  | c1, 10 prompts, 256 tokens (`src/single_check.py`): not argmax | 3.39 % | 2.05 % |
  | c1: gap > 1 / max gap | 4 / 2.0 | 5 / 3.0 |
  | c1: mean \|decode − teacher-forced logprob\| | 0.045 | 0.044 |
  | c30 concurrent (`conc_check.py`): not argmax | 3.67 % (earlier persist runs: 3.09, 2.33, 2.29 %) | 2.71 % (earlier: 3.11, 2.48 %) |
  | c30: gap > 1 / max gap | 10 / 3.5 | 5 / 1.1 (earlier max 1.5–1.75) |

  The ranges overlap. No systematic error shows, which is expected because the kernels reproduce TRT-LLM's
  non-split-K arithmetic bit for bit.

## What limits it now
* **Host-bound regime** (above about 11 cold experts per layer at T = 64; above about 2 at T = 6).
  * Time is cold experts × 17.7 MB / ~380 GB/s, which is about 46 µs per cold expert.
  * ncu shows 374–379 GB/s against the ~385–390 GB/s C2C ceiling.
  * The only remaining lever is fewer host bytes: more HBM, or prediction or prefetch across layers.
  * The c32 server runs show 5.5–5.9 % DRAM share of routed selections, which is about 15–18 cold experts per layer per
    step, so c32 is mostly in this regime.
* **HBM-bound regime** (few cold experts). The kernels stream HBM at 5.9–6.1 TB/s, the same as TRT-LLM.
  * T = 64 is at parity or slightly ahead.
  * T = 32 with 0–2 cold experts is 2–4 % slower than TRT-LLM `8:71`. This comes from the GEMM1 tail (27.5 items per CTA) plus the front.
  * `MOE_PERSIST_CTAK=512,128 MOE_PERSIST_STAGES=3,10` (GEMM1 K-tile 512, bit-identical) gains about 1 % there. It is not the default.
* **Fixed costs per layer.** The front is about 4–8 µs, although PDL lets GEMM1's launch and prologue overlap it.
  The GEMM1→GEMM2 boundary costs about 2 µs.
* **Split model.** It was swept (`sweeps/v2-*.log`): `kc` max 12, 16 or 24, the bandwidth model, and stage depths.
  All results land within ±1 %, so the static split is not the bottleneck and the v2 dynamic queue was not needed.

## Knobs (env, all `MOE_PERSIST_*` are passed through by the start scripts)
| knob | default | meaning |
|---|---|---|
| `MOE_PERSIST` | 1 in the candidate script | 1 enables the persistent path; 0 is exactly production |
| `MOE_PERSIST_MAX_TOKENS` | 128 | largest call taken; larger calls go to TRT-LLM. 192 is tested and works |
| `MOE_PERSIST_STAGES` | `6,10` | TMA stages of GEMM1, GEMM2 |
| `MOE_PERSIST_CTAK` | `256,128` | K-tile of GEMM1, GEMM2; `512,128` with stages `3,10` is also bit-identical |
| `MOE_PERSIST_KC` | `4,16` | minimum / maximum cold CTAs per GEMM |
| `MOE_PERSIST_BW` | `385,6000,46` | split model: host GB/s, HBM GB/s, per-CTA GB/s |
| `MOE_PERSIST_LAYERS` | `all` | e.g. `0-9,20` for bisecting |
| `MOE_PERSIST_FRONT` | 2 | front kernel version; 1 is the first version |
| `MOE_PERSIST_PDL` | 1 | PDL on the front and finalize |
| `MOE_PERSIST_WARM` | 1 | at bind, run every capture size once (Triton compile before graph capture) |

To promote, copy `cand/plugin/moe_placement/{persist_moe,persist_moe_cute,persist_front}.py` and the two hook blocks
in `__init__.py` into `~/dsv41/moe/plugin`, and add `-e MOE_PERSIST=1` to `serve-moe.sh`. Equivalently, use
`cand/serve-moe-persist.sh`.
